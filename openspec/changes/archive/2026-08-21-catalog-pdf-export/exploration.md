## Exploration: catalog-pdf-export

### Current State

The public catalog page is `apps/web/src/app/(marketing)/catalogo/page.tsx`. Its export area currently renders two actions: a primary link to `/catalogo/imprimir` labeled `Imprimir / PDF`, and a secondary downloadable link to `/api/catalog/export` labeled `Exportar datos JSON`. The requested scope therefore includes removing the visible JSON link while deciding separately whether the technical JSON route should remain as an undocumented/internal endpoint.

`/catalogo/imprimir` is not a server-side PDF generator. `apps/web/src/app/(marketing)/catalogo/imprimir/page.tsx` is a server-rendered, print-oriented HTML page with `dynamic = "force-dynamic"`; it calls `getAllProducts()`, groups products by category, and relies on browser `window.print()` through `PrintButton.tsx` to let the visitor save a PDF. The current print layout has a toolbar, one text header, category sections, and flat product rows with measurements/materials. It has no cover, table of contents, product images, branded page composition, or explicit page-number treatment. Print CSS hides the marketing header/footer/nav and uses A4 landscape, page breaks, and `break-inside: avoid` for rows.

The JSON route is `apps/web/src/app/api/catalog/export/route.ts`. It is a Node.js, force-dynamic GET route that calls `getAllProducts()`, returns an attachment named `catalogo-ene-muebles.json`, and explicitly sends `Cache-Control: no-store`. It is covered by `route.test.ts`. `getAllProducts()` in `apps/web/src/lib/strapi.ts` paginates active products in batches of 100 with `populate=*`, sorts by `order`, normalizes media, and attaches the `catalog` cache tag to each Strapi fetch. The helper comment still describes JSON export as its consumer, so the PDF work should rename/document the shared catalog snapshot helper rather than leave an inaccurate ownership comment.

Product/category data is already CMS-backed and sufficiently rich for the requested catalog: `Product` includes name, slug, description/short description, price/currency, dimensions, materials, category, subcategory/product type, usage environment, observable color/material, and up to eight images; `Category` includes name, slug, description, image, order, and active state. The Strapi schemas are `apps/cms/src/api/product/content-types/product/schema.json` and `apps/cms/src/api/category/content-types/category/schema.json`. The public query filters active products/categories and uses `populate=*`, but there is no explicit published-status parameter in the public product helper; Strapi draft-and-publish is enabled, so proposal/design should confirm the intended public publication semantics before changing the PDF query.

Media normalization in `strapi.ts` converts relative upload URLs to `NEXT_PUBLIC_STRAPI_URL`/public Strapi origin, preserves original dimensions/alt text, and exposes `pickMediaFormat()` for slot-aware responsive formats. The existing web image path uses `next/image` with `unoptimized: true` in `apps/web/next.config.ts`, because the project deliberately avoids the Next image optimizer for Strapi uploads. The print page currently renders no images. Product cards demonstrate the established image/alt fallback pattern in `apps/web/src/components/ProductCard.tsx`; product images are uploaded and reordered through the admin routes, with an eight-image/product and 5 MB/file limit documented in `openspec/specs/admin-product-images/spec.md`.

Branding already has a clear, reusable identity: `packages/ui-tokens/src/tokens.css` and `src/colors.ts` define ink `#2C2C2C`, taupe `#A69076`, cream `#EBE2D9`, paper `#F9F8F6`, text-safe aliases, and Hanken Grotesk plus a limited Source Serif 4 display use. `packages/ui-tokens/src/site.ts` owns brand/copy tokens such as `ENE-MUEBLES`, `Catálogo 2026`, dispatch coverage, and navigation. The root layout loads Hanken Grotesk and Source Serif 4 and sets `lang="es-CL"`. Public logo files were observed under `images/` (including `logoenemue-horizontal.png`, `enem-logo-horizontal-blanco.png`, `ene-logocuadradoblanco.png`, and `ene-logocuadrado.png`); web-public product/reference images also exist under `apps/web/public/images/`. The exact logo variant and dimensions should be verified during design implementation rather than guessed.

Caching is already aligned with a modest-traffic CMS-backed site. `strapi.ts` applies `next: { revalidate: 60, tags: [...] }` to public Strapi reads. `STRAPI_CACHE_TAGS.catalog` covers products/categories/media, and admin product/category/image mutation routes call `revalidateTag("catalog", { expire: 0 })` after successful writes. Thus the current print page is request-time HTML, but its CMS data reads are normally served from the Next data cache for 60 seconds and can be invalidated immediately through the existing admin paths. The print page itself has no response cache header because it is HTML rendered inside the marketing layout; the JSON route deliberately bypasses response caching.

The repository is a pnpm workspace using Node.js 20, Next.js 16.2.9, React 19.2, TypeScript 5.6, Tailwind CSS 4.1, and Strapi 5.2. The web dependencies contain no PDF renderer (`pdfkit`, `pdf-lib`, `@react-pdf/*`, Puppeteer, or similar). Playwright is present only as a root dev dependency and is not configured as an E2E runner; there is no production browser dependency or existing server-side PDF pipeline. Existing tests are Vitest unit/component tests, including `catalogo/page.test.tsx`, `catalogo/imprimir/page.test.tsx`, `api/catalog/export/route.test.ts`, and Strapi helper tests. The current catalog tests explicitly expect the JSON action to remain visible and will need to change with the feature.

### Approaches

1. **Request-time print HTML with cached/revalidated CMS snapshot (recommended)** — keep `/catalogo/imprimir` as a server-rendered HTML document saved through the browser's print dialog. Fetch the complete active/published snapshot at request time, relying on the existing 60-second tagged Strapi data cache and immediate `catalog` tag invalidation after admin changes. Render the branded cover, TOC, category sections, image-backed product cards, and CSS print headers/footers/page-number mechanisms.
   - Pros: uses the current working runtime and deployment model; no new binary/PDF dependency or headless browser; current product/media data at generation time within the defined cache window; easy to make editable/versionable; browser print handles PDF creation without server CPU/memory cost; low operational risk for modest traffic.
   - Cons: output is technically print HTML until the visitor chooses Save as PDF; browser engines differ in pagination and support for CSS counters/headers; product images must be reachable by the visitor's browser; cache freshness is normally up to 60 seconds unless tag invalidation is used.
   - Effort: Medium.

2. **On-demand server-generated binary PDF route** — add a PDF renderer such as `@react-pdf/renderer`/`pdfkit`, or run a managed/headless Chromium process, and return `application/pdf` from a route that builds the document from the live snapshot.
   - Pros: consistent downloadable PDF bytes, deterministic file response, server-controlled page numbers and layout, can preserve the JSON route only as an internal API if needed.
   - Cons: introduces a new runtime dependency and deployment complexity; image fetching/decoding and PDF layout consume CPU/memory per request; headless Chromium is especially heavy and is not currently installed/configured; font/image loading and pagination have new failure modes; without a cache/lock, repeated clicks can overload the modest site.
   - Effort: High.

3. **Prebuilt snapshot generated after CMS changes** — generate a PDF artifact asynchronously or during an admin-triggered job, store it, and serve the latest completed version.
   - Pros: cheapest and fastest public download; generation load is isolated and deduplicated; stable output for sharing/printing; strong protection against request spikes.
   - Cons: requires storage, job orchestration, invalidation/status UX, and a policy for partial/failed generations; edits are not visible until regeneration completes; no existing artifact store or background worker is present; more backend/ops scope than this change currently warrants.
   - Effort: High.

### Recommendation

Use Approach 1 for this change: a branded, server-rendered print catalog that is live at request time while its Strapi data reads are cached for 60 seconds and invalidated by the existing `catalog` tag after successful admin product/category/image mutations. This is the safest fit for the current Node/Next/Coolify runtime and modest traffic: it avoids introducing a server PDF engine and therefore avoids the largest overload risk. Add a bounded in-process request guard only if implementation profiling shows the full snapshot is expensive; do not add an unproven global rate limiter that could break legitimate printing. The document should use explicit, stable print CSS and semantic hooks for page breaks, TOC entries, product cards, header/footer, and page-number counters, with graceful image placeholders and bounded description lengths.

Keep the JSON route decision explicit in proposal/spec: the user request removes the visible action, not necessarily the API. Safest compatibility choice is to leave `/api/catalog/export` functioning but unlinked and document it as a technical endpoint; remove it only if the owner confirms API removal is intended. If a true downloadable PDF file is a hard requirement rather than browser Save as PDF, make that a separate design decision (prefer a cached/prebuilt or single-flight generation service over unbounded per-request Chromium).

### Risks

- Browser print pagination is not fully deterministic across Chrome/Firefox/Safari; CSS counters, page breaks, and repeating header/footer behavior require browser verification at the target A4 orientation and representative product counts.
- `force-dynamic` keeps the page request-time, but the shared Strapi fetch cache means “live” is bounded by the 60-second revalidation window unless the admin mutation invalidation path is used. Direct edits in Strapi Admin outside the Next admin routes may remain stale until expiry.
- `populate=*` across all products and images can grow with the catalog; the current helper is paginated but still transfers full product/media payloads. A print-specific query should avoid unnecessary fields/relations while retaining the image formats needed for print.
- Public image URLs must be reachable from the visitor's browser and must not depend on the internal Docker hostname. Missing/blocked/CORS-sensitive media must degrade to an intentional placeholder rather than producing broken cards.
- A true server PDF implementation would materially increase CPU/memory and deployment risk because no PDF runtime exists today. It should not be smuggled into the print-layout change without an explicit load/caching plan.
- Product descriptions, prices, materials, and dimensions may be incomplete or contain unverified business claims. The PDF must render available CMS data without inventing missing values and should define whether prices are included in an institutional catalog.
- Category names/order and products can change between the TOC query and the product snapshot if separate requests are used; prefer one coherent snapshot or deterministic grouping from the same fetched dataset.
- Existing tests encode the current JSON-visible behavior and old toolbar label; changing the UI without updating them will create false failures, while insufficient new assertions could allow a regression to a text-only catalog.
- The repository contains reference/catalog files under `carga/` and logo/image assets, but they are not a runtime PDF pipeline. Do not treat the supplied 26-page reference or those files as authoritative CMS content without a verified mapping.

### Ready for Proposal

Yes. The repository has enough evidence to write the proposal and design. The proposal should state that “PDF” means a branded print-ready catalog saved by the browser, unless the owner explicitly requires a server-produced binary file; it should also record the compatibility choice to keep the JSON route unlinked versus removing it. The next phase should define frontend requirements for cover/TOC/cards/print CSS and a separate backend/data requirement for coherent active/published snapshots, media handling, cache freshness, and load protection.
